# IoT Monitoring System

We are building an **IoT monitoring system** to collect, process, and analyze device data.
Sensors (temperature, humidity, atmospheric pressure) send readings to a Spring Boot backend,
which stores them in PostgreSQL and raises alerts. A React frontend displays the data.

The original assignment is described in [TASKS.md](./TASKS.md).

## How to run

All commands are run from the repository root.

### Requirements

- Java 21 and Maven
- Docker (PostgreSQL and Kafka, and also for the Testcontainers-based tests)
- Node.js 20 or newer (frontend)

### 1. Infrastructure

```bash
cd backend
docker compose up -d
```

This starts PostgreSQL (`localhost:5432`, database `monitoring`) and Kafka (`localhost:9092`).
The connection settings in `backend/src/main/resources/application.properties` match this
compose file.

### 2. Backend

```bash
cd backend
mvn spring-boot:run
```

The backend runs on `http://localhost:8080`.

The schema is generated by Hibernate with `ddl-auto=create-drop`, so **the database is empty
after every restart**. Create some sensors first:

```bash
curl -X POST http://localhost:8080/sensors \
  -H "Content-Type: application/json" \
  -d '{"name": "Living room", "type": "TEMPERATURE"}'
```

Valid sensor types: `TEMPERATURE`, `HUMIDITY`, `ATMOSPHERIC_PRESSURE`.

### 3. Frontend

```bash
cd frontend
npm install
npm run dev
```

The app is available at `http://localhost:5173`.

API calls go through the Vite dev server proxy (`frontend/vite.config.ts`) to
`http://localhost:8080` for `/sensors`, `/sensor-readings` and `/alerts`, so no CORS
configuration is needed on the backend. The proxy returns `index.html` when the browser requests
an HTML page (e.g. F5 on `/sensors`), so client-side routes do not collide with API paths of
the same prefix.

## REST API

| Method | Path | Description |
|--------|------|-------------|
| GET | `/sensors` | all sensors |
| POST | `/sensors` | create a sensor (`name`, `type`); `400` if the name is empty, `409` if it already exists |
| GET | `/sensor-readings` | all readings |
| GET | `/sensor-readings/{sensorId}` | readings of one sensor |
| POST | `/sensor-readings` | body `{ sensorId, value, timestamp }`, returns the saved reading |
| GET | `/alerts` | all alerts as `[{ sensorId, message, timestamp }]` |
| GET | `/alerts/latest?sensorId=<uuid>` | most recent alert of a sensor; `404` if there is none |

Kafka:

- consumed: `sensor-reading` (saved as a reading) and `sensor-alerts` (saved as an alert)
- produced: every saved alert is published to the `alerts` topic as an `AlertDto`

## Implemented tasks

- **Task 1:** `Sensor.type` is stored as a string (`@Enumerated(EnumType.STRING)`).
- **Task 2:** `Sensor` has one-to-many relations to `SensorReading` and `Alert`; both reference
  the sensor through the `sensor_id` foreign key.
- **Task 3:** `SensorReadingService.saveSensorReading` persists readings (HTTP and Kafka).
- **Task 4:** `POST /sensors` returns `400` for a missing name and `409` for a duplicate name.
- **Task 5:** `GET /alerts/latest?sensorId=...`.
- **Task 6:** `AlertService.saveAlert` stores the alert and publishes it to the `alerts` topic.
- **Task 7:** average temperature in a period, rounded to one decimal.
- **Task 8:** measurement values by sensor type, ordered by timestamp.
- **Tasks 9 and 10:** `filterByAverageDeviation` and `getMovingAverage`.

## Decisions

- **GET endpoints:** three GET endpoints were added so the frontend can retrieve all data:
  `AlertController/getAllAlerts`, `SensorController/getAllSensors` and
  `SensorReadingController/getAllSensorReadings`.
- **DTO for alerts:** the `Alert` entity hides its `sensor` field from JSON (`@JsonIgnore`), so
  `GET /alerts` returns `AlertDto` objects. This gives the frontend the `sensorId` without
  serializing the entity graph (and without lazy-loading problems).
- **Filtering and rounding in the database:** the average temperature (Task 7) and the ordered
  values by sensor type (Task 8) are JPQL queries instead of in-memory processing.
- **Polling for alerts (frontend):** `/alerts` fetches every 5 seconds (`setInterval` in
  `useEffect`, cleaned up on unmount). Chosen over WebSocket/SSE because the backend only
  exposes plain REST endpoints.
- **Sensor names on the client:** the alerts endpoint returns only `sensorId`, so the frontend
  looks names up from `GET /sensors` (loaded once) and falls back to the UUID.
- **Sorting:** alerts are sorted on the client by timestamp, newest first.
- **Form validation (frontend):** the value must be a number (a comma is accepted as the decimal
  separator), the timestamp must be a valid date, not in the future, and in a realistic year
  range. Failed requests show an error message.
- **Timestamps:** the backend uses `LocalDateTime` (no timezone), so the form sends the local
  date-time string of the `datetime-local` input as is (e.g. `2026-11-24T15:10:00`) instead
  of a UTC `Date` with a `Z` suffix, which would shift the stored time by the timezone offset.
- **Axios instance and interceptor** in `services/api.ts`: one place for the base URL and
  HTTP error handling.

## Assumptions

- Timestamps are ISO-8601 local date-times without a timezone.
- Sensor ids are UUIDs (strings in JSON).
- No authentication.
- The frontend only runs against the local backend through the Vite proxy.

## Known limitations

- Polling instead of push (WebSocket/SSE).
- No pagination for readings and alerts.
- Alerts can only be created through Kafka (`sensor-alerts`); there is no `POST /alerts`.
- The frontend has no "add sensor" form; sensors are created through the API.
- The database is recreated on every start (`create-drop`), so there is no persistence between runs.
- Frontend tests cover only the `SensorPage` component and the `api.ts` service.
